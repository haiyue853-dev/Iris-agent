# RAG 知识库优化面试总结

## 一、项目背景

我实现了一个面向 Agent 技术资料的本地 RAG 知识库，并使用包含 80 道 Agent 面试题的文档进行检索评测。

最终检索链路包括：

- 本地 `bge-m3` 向量化
- 自适应语义切分与父子切片
- BM25 关键词召回
- 向量召回
- 知识图谱召回
- RRF 多路融合
- 本地 `qwen3.5:4b` 重排
- MMR 结果去重
- `[1][2]` 可点击知识引用

整体目标不是简单实现“能搜索”，而是解决文档切分、召回、排序、评测和用户真实问法之间的工程问题。

## 二、面试完整回答

我在优化知识库时，主要遇到了五类问题。

### 1. 本地模型接口返回 502

最初导入文档时，Ollama 的 embedding 接口返回 `502 Bad Gateway`。

排查后发现，问题并不在 embedding 模型本身，而是 HTTP 客户端继承了系统代理配置，导致访问 `localhost` 时也可能经过代理。

解决方案是：

- 本地 Ollama 客户端统一设置 `trust_env=False`，不继承系统代理。
- embedding 和兼容接口均进行异常处理。
- 健康检查不再只判断端口和模型是否存在，而是执行一次真实模型调用。

这个问题让我意识到：模型出现在 Ollama 模型列表中，不代表整个调用链真的可用。

### 2. 文档切分导致上下文丢失

原文中的编号列表容易被误判为一级标题，导致一个完整答案被拆成多个互相独立的切片。

例如第 75 题的答案内部包含 1～7 条编号列表，最初只有主切片被标注为正确答案，其他答案片段没有进入相关切片集合，因此出现了假性召回失败。

解决方案是：

- 使用本地 `bge-m3` 进行自适应语义切分。
- 引入父子分块：子块用于精确召回，父块用于补充完整上下文。
- 保留标题和问题边界，避免把答案内部的普通编号当成新问题。
- 对跨多个切片的答案标注多个 `relevant_chunk_ids`。

这样既保留了小切片的召回精度，也避免最终交给大模型的内容过于零碎。

### 3. 重排模型看似在线，实际无法稳定工作

最初的重排健康检查只确认 Ollama 中是否安装了模型，但真实调用时仍可能出现两类问题：

- HTTP 请求受代理影响并返回 502。
- 部分生成模型在 JSON 模式下返回空对象，无法得到候选分数。

解决方案是：

- 重排客户端同样关闭系统代理。
- 健康检查执行一次真实的 `query-document` 打分。
- 将本地重排模型切换为 `qwen3.5:4b`。
- 使用严格 JSON Schema 约束输出格式。
- 设置 `think: false`，避免思考内容污染结构化结果。
- 要求每个候选切片都返回对应分数。

优化后，重排链路可以真实参与搜索，而不是只在配置页面显示“已连接”。

### 4. 评测标签会制造假性失败

在困难问题测试中，用户询问 Cross-Encoder 重排性能时，系统从另一份 RAG 文档中找到了语义正确的答案，但评测标签只认可 80 题文档里的切片，因此被错误判断为未命中。

解决方案是：

- 一个问题允许对应多个正确切片。
- 允许正确答案分布在不同文档中。
- 分析失败案例时，区分召回失败、排序失败、切分问题和标注漏标。
- 在调整检索算法前，先人工检查 Top 结果是否实际正确。

这避免了为了迎合错误标签而修改召回逻辑。

### 5. 用户不会完全按照原题提问

原题评测效果很好，但用户换成口语化表达后，部分答案只能排到第二名。

例如：

> 资料明明已经删掉了，机器人为什么还会搜出旧答案？这种脏召回该怎么彻底处理？

原始知识标题使用的是“文档删除、向量库实时一致性、旧知识和脏数据”等术语，口语表达与文档关键词之间存在差距。

解决方案是增加轻量查询改写：

1. 保留用户原始问题。
2. 识别常见口语表达和技术简称。
3. 追加规范领域词，例如“文档删除、向量库实时一致性、旧知识、脏数据”。
4. 扩展后的查询用于关键词、图谱和向量召回。
5. 重排仍然使用用户原句，防止扩展词改变用户真实意图。

该方案不需要额外调用 LLM，因此基本不会增加检索延迟，同时减少了模型改写可能造成的语义漂移。

## 三、问题、原因与解决方案汇总

| 问题 | 根本原因 | 解决方案 |
| --- | --- | --- |
| Ollama embedding 返回 502 | 本地请求错误继承系统代理 | HTTP 客户端设置 `trust_env=False`，增加真实调用检查 |
| 长答案内容丢失 | 编号列表被误判成标题，切片过碎 | 自适应语义切分、父子分块、保护标题边界 |
| 重排显示在线但没有生效 | 健康检查只检查模型列表，模型输出格式不稳定 | 执行真实打分，使用严格 JSON Schema 和 `think: false` |
| 正确结果被评测为失败 | 标签只认可单一文档或单一切片 | 支持多相关切片和跨文档正确答案 |
| 口语问题首位排序不稳定 | 用户措辞与知识库标准术语不一致 | 保留原问题并追加规范检索词，原句继续用于重排 |
| 生成式重排耗时较高 | `qwen3.5:4b` 需要逐候选执行生成式评分 | 当前优先保证准确率，后续可替换轻量 Cross-Encoder |

## 四、评测方案

为了避免只测试“照抄原文”的问题，我把评测集分成三层。

### 1. 原始问题集

- 80 条原始面试题。
- 用于验证基础切分、召回和排序能力。

### 2. 口语化改写集

- 40 条口语化改写问题。
- 减少原题关键词，验证语义泛化能力。

### 3. 困难问题集

- 20 条人工设计的困难问法。
- 7 条模糊表达。
- 7 条技术简称或工程黑话。
- 6 条上下文指代式追问。

主要指标包括：

- Hit@1
- Hit@3
- Recall@K
- MRR
- NDCG@K
- 各检索路由覆盖量

## 五、优化效果

### 初始 80 题基线

- Hit@1：70%
- Hit@3：82.5%
- MRR：0.784

### 完成混合召回和重排优化后

- Hit@1：88.7%
- Hit@3：98.8%
- MRR：0.935

### 40 条口语化问题

- Hit@1：82.5%
- Hit@3：97.5%
- Hit@5：100%
- MRR：0.902

### 20 条困难问法完成查询改写后

- Hit@1：100%
- Hit@3：100%
- Hit@5：100%
- MRR：1.0
- 模糊表达：7/7 Top 1
- 技术简称：7/7 Top 1
- 指代追问：6/6 Top 1

不同测试集的指标分别统计，不能简单合并成一个总分。

## 六、一分钟面试回答

我做 RAG 优化时，没有只关注向量模型，而是分别处理了数据、召回、排序和评测四个环节。

数据层使用本地 `bge-m3` 做语义切分和向量化，并通过父子分块解决长答案上下文丢失。召回层采用 BM25、向量和知识图谱多路召回，再通过 RRF 融合。排序层使用本地 `qwen3.5:4b` 重排，并通过真实打分健康检查和严格 JSON Schema，解决模型看似在线但实际不可用的问题。

针对用户口语化和模糊化提问，我加入了零额外模型调用的查询改写：扩展词用于提高召回，用户原句继续负责重排，从而降低语义漂移风险。

此外，我发现评测标签本身也可能制造假性失败，所以支持一个问题对应多个正确切片以及跨文档正确答案。最终原题 Hit@3 从 82.5% 提升到 98.8%，20 条困难问法达到 100% Top 1。

## 七、可以重点强调的工程亮点

- 全程使用本地模型，知识数据不出域。
- 入库和查询始终使用同一个 embedding 模型，保证向量空间一致。
- 健康检查验证真实模型能力，而不是只检查端口或模型列表。
- 保留原始查询并扩展召回词，降低查询改写的语义漂移风险。
- 使用关键词、向量和知识图谱多路召回，降低单一路线的漏召回概率。
- 区分真实召回失败、排序失败、切分问题和评测标注错误。
- 使用原题、口语改写题和困难题进行分层评测。
- 检索结果支持 `[1][2]` 知识引用，方便定位原始依据。

## 八、当前不足与后续优化

当前方案的主要瓶颈是生成式重排延迟。`qwen3.5:4b` 的准确率较好，但逐候选生成分数的速度不适合更高并发场景。

后续可以继续优化：

1. 使用轻量 Cross-Encoder 或专用 reranker 替代生成式重排。
2. 对重排请求进行动态 batching。
3. 缓存重复或近似查询的召回结果。
4. 增加真实用户日志构建的困难评测集，降低模型生成测试题带来的偏差。
5. 持续保存 Top 3 未命中案例，形成可回归的 bad case 数据集。

## 九、总结

这次优化的核心经验是：RAG 效果不好时，不能直接归因于 embedding 模型。

真正影响效果的因素包括文档切分、查询表达、候选召回、融合排序、重排稳定性以及评测标签质量。只有把每个阶段拆开观察并通过可重复的评测数据验证，才能判断问题究竟发生在哪里，并避免盲目更换模型或调整参数。
