# 聊天与工具协作式取消设计

## 目标

用户点击聊天输入框中的停止按钮后，立即停止当前 AI 工作流，并让所有仍在运行的工具状态停止转圈、显示为已停止。

## 当前问题

前端停止按钮只中断浏览器端响应流。后端工具通过同步 `registry.invoke()` 执行，客户端断流不能中断已进入的工具处理函数，因此工具仍可能继续运行，前端工具项也会停留在运行状态。

## 取消语义

1. 点击停止后，前端立即将当前助手消息标记为 `cancelled`。
2. 当前消息中所有尚未完成的工具项立即显示“已停止”，不再显示旋转状态。
3. 前端保存流返回的 `task_id`，停止时调用现有任务取消接口，并同时终止本地响应流。
4. 后端为当前聊天执行建立线程安全的取消信号。
5. 每次模型请求前、每个工具开始前、工具返回后以及下一轮模型请求前检查取消信号。
6. 收到取消后不再启动新的模型请求或工具调用，也不持久化取消后迟到的工具结果。
7. 支持取消信号的工具应尽快退出；无法中断的第三方同步调用允许自然返回，但返回结果必须丢弃，AI 工作流不得继续。
8. 重复取消是幂等操作；已完成、已失败或已停止的任务保持其终态。

## 前端数据流

- `task_started` 事件中的 `task_id` 保存到当前 adapter 运行实例。
- assistant-ui 的取消信号触发时：
  - 立即结束本地生成状态；
  - 如果已有 `task_id`，请求 `DELETE /api/tasks/{task_id}`；
  - 如果取消发生在 `task_started` 到达前，在取得 `task_id` 后立即补发取消请求。
- adapter 以 `{ type: "incomplete", reason: "cancelled" }` 结束当前消息。
- 未完成工具调用映射为取消状态，工具分组与单项工具均显示“已停止”。

## 后端数据流

- 聊天流创建任务后，将 `task_id` 与本次 Agent 执行关联。
- 任务取消接口设置该执行的取消信号，而不仅是修改任务中心状态。
- AgentLoop 在模型和工具边界检查取消信号；取消后发出明确的取消终止事件或结束执行。
- 工具返回时若取消信号已设置，不发送 `tool_finished` 成功结果，不继续下一轮。
- 流断开仍作为兜底设置停止状态并清理待审批调用。

## 工具边界

- 本次不把所有工具迁移到独立进程，也不强杀 Python 线程。
- 文件读写等短工具通常会在取消前后边界快速停止。
- HTTP、MCP 或其他不可协作的同步调用可能继续到自身超时，但其结果不会被 AI 使用。
- 后续可为特定长耗时工具增加取消令牌支持，不改变本次公共取消语义。

## 界面状态

- 运行中：保持现有旋转状态。
- 用户停止：显示“已停止”，使用中性弱化样式，不显示为执行失败。
- 已完成工具保持完成状态，不因停止其他工具而改变。
- 停止后输入框恢复可用，用户可以立即发送下一条消息。

## 验证

- 模型流式输出中点击停止：消息进入 cancelled，后端任务停止。
- 工具执行中点击停止：工具立即停止转圈并显示“已停止”。
- 取消发生在收到 `task_id` 前：收到后补发一次取消请求。
- 工具迟到返回：结果被丢弃，不再触发下一轮模型调用。
- 一个工具完成后停止：已完成工具保留完成状态，后续工具不启动。
- 重复停止：后端取消请求与终态处理保持幂等。
- 前后端完整测试、前端构建和 lint 检查通过。
