# Agent 任务中心设计

日期：2026-08-13  
状态：方案已确认，等待书面规格审查

## 目标

为每次主聊天 Agent 执行提供一个可回看的任务记录：用户可以在前端任务中心查看当前与近期任务、执行状态、工具阶段和审批结果，并可从聊天直接跳转到对应任务。

第一期只追踪聊天与 MCP 工具的执行过程；它不是后台队列，也不提供任务取消、恢复、重试、调度或产物管理。

## 用户体验

侧栏新增“任务中心”入口，沿用 Iris 现有的中性底色、紫色强调色与卡片层级。页面左侧是按最近活动排序的任务列表，右侧为当前任务的时间线。

任务列表显示：请求摘要、状态、关联会话、最后活动时间。时间线显示固定的安全阶段说明、工具名称、成功或失败状态、耗时和审批结论；不显示工具参数、工具返回值、环境变量、原始异常或模型回复全文。

聊天接口开始执行时会先返回 `task_started` 流事件，前端据此保存当前任务 ID。聊天区域显示“查看任务”入口，点击后进入任务中心并选中该任务。审批继续沿用现有会话和工具调用 ID，任务中心不引入新的审批机制。

## 生命周期

每次 `POST /api/chat/stream` 在确认会话存在后创建一条任务记录。任务与 `session_id` 绑定，请求摘要取用户消息去除首尾空白后的前 120 个字符，不经模型生成。

任务状态仅有：

- `running`：已开始执行，或批准工具后继续执行。
- `awaiting_approval`：等待用户批准或拒绝工具调用。
- `completed`：模型回复完成，或拒绝工具后后续对话正常完成。
- `failed`：流内已知错误或服务内部错误。
- `stopped`：客户端断开、流被停止，或服务重启前未完成。

事件从现有 Agent 流旁路映射：

| 原始事件 / 情况 | 任务状态 | 保存的安全事件 |
| --- | --- | --- |
| 创建聊天流 | `running` | “已提交请求” |
| `text_delta` | 不变 | 仅更新活动时间，不保存回复文本 |
| `tool_started` | `running` | “开始调用工具：&lt;工具名&gt;” |
| `tool_approval_requested` | `awaiting_approval` | “等待工具审批：&lt;工具名&gt;” |
| 审批接口被调用 | `running` | “已批准/已拒绝工具调用：&lt;工具名&gt;” |
| `tool_finished` | `running` | “工具调用成功/失败：&lt;工具名&gt;”，可含耗时 |
| `message_completed` | `completed` | “已生成回复” |
| 已知或未处理错误 | `failed` | 固定的安全失败摘要，不保存异常详情 |
| 客户端停止或服务重启恢复 | `stopped` | “执行已中断” |

客户端中止通过流生成器的 `GeneratorExit` / 清理路径标记。任务中心不显示停止按钮；已有聊天停止按钮仍然生效，只改变任务记录状态。

## 后端边界与存储

新增独立的 `iris_agent/task_center/` 模块，职责是任务账本、状态转换、事件裁剪与读取。它不修改 `AgentLoop` 的推理或工具执行语义，也不写入会话消息。

新增 `TaskCenterSettings`，默认目录为 `data/tasks`。账本位于 `data/tasks/tasks.json`，使用临时文件替换写入。账本最多保留最近活动的 100 条任务；每条任务最多保留最近的 100 个事件。写入前裁剪旧记录，读取列表时不携带完整事件。

建议模型：

```text
AgentTask
  id, session_id, request_summary, status
  created_at, updated_at, finished_at?
  events: TaskEvent[]

TaskEvent
  id, type, label, created_at
  tool_name?, duration_ms?
```

`TaskEvent` 不具备保存任意 payload 的字段。任务服务只接受事件种类、固定标签、工具名和数值耗时，以结构约束防止将敏感调用数据误写入账本。

启动时，所有 `running` 与 `awaiting_approval` 的旧任务都转为 `stopped` 并写入“服务重启，执行未完成”事件。第一期不尝试恢复模型上下文、工具进程或待审批状态。

`create_app` 以可选依赖注入任务中心服务，保持现有 API 测试构造方式兼容。正式启动时由 `bootstrap.py` 创建服务、由 `server.py` 注入应用。

## API 与流协议

新增只读 API：

- `GET /api/tasks?limit=50&session_id=<optional>`：返回任务摘要，默认最多 50 条，服务端上限 100。
- `GET /api/tasks/{task_id}`：返回单条任务和其安全事件时间线；不存在时返回稳定的 404 错误码。

`POST /api/chat/stream` 在既有 NDJSON 事件之前发出：

```json
{"type":"task_started","data":{"task_id":"task_..."}}
```

前端只用此 ID 做跳转；后续任务详情均从只读 API 获取。审批接口不需要携带任务 ID：服务按 `(session_id, call_id)` 找到正在等待审批的任务并写入审批、工具结果和后续生命周期事件。

## 前端接入

新增 `tasks` 视图、`TaskCenterPage`、任务 API 客户端与任务类型定义。页面加载时请求摘要列表，选择一项后请求详情；出现错误时显示页面内安全提示与重试入口。

`useChat` 处理 `task_started`，维护当前任务 ID，并在开始新聊天、切换会话或任务结束后保持最后一个可查看的任务 ID。`App` 负责从聊天传入任务跳转回调：切换到 `tasks` 并把任务 ID 交给任务页选中。任务中心只读取数据，不改变任务状态。

## 测试与验收

后端测试覆盖：

- 创建、工具开始/结束、审批、完成、失败和中断的状态转换；
- 重启恢复把未完成任务转为 `stopped`；
- 100 条任务与 100 个事件的保留上限；
- 工具参数、工具结果、环境变量值、原始异常和模型回复不会写入 JSON 账本；
- 聊天流返回 `task_started`，审批流能关联已有任务；
- 列表与详情 API 的响应、过滤和不存在任务错误。

前端测试覆盖：

- 侧栏可打开任务中心并保留视图；
- 任务列表、状态标签、时间线和加载失败提示；
- 聊天收到 `task_started` 后，“查看任务”可跳转并选中该记录；
- 任务页不渲染接口中意外出现的敏感详情字段。

验收标准是：一次普通回复、一次 MCP 工具调用和一次需要审批的工具调用都能在任务中心形成可读、可跳转的完整安全时间线；会话与现有审批行为保持不变；任务账本在重启后保留历史但不会假装恢复未完成执行。
