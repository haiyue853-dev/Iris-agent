# 后台任务队列一期设计

日期：2026-08-14  
状态：方案已确认，等待书面规格审查

## 目标与范围

将主聊天的默认执行方式改为后台任务队列。用户提交消息后立即获得任务状态，Agent 在后台依次执行；前端在任务完成后刷新会话并展示完整回复。

一期采用进程内单工作者和 JSON 账本，不引入外部消息队列、分布式工作者、自动重试、定时调度或逐字流式输出。现有登录工作继续暂缓。

现有 `POST /api/chat/stream` 保留为兼容接口，不改写为队列协议；React 聊天界面改用新任务接口。单工作者并发约束仅适用于新的后台队列入口。

## 方案选择

比较过以下方案：

- 进程内单工作者 + JSON 账本：无需新服务，能复用会话、任务中心和原子 JSON 仓储；适合一期。
- 多工作者并发队列：吞吐量更高，但会增加会话排序、工具审批和取消的并发复杂度。
- 外部队列服务：可跨进程恢复，但需要 Redis 等额外运维依赖。

本期选择第一种方案。任务在同一时刻只允许一个 Agent 执行；等待工具审批的任务也会占用该工作者，直到被批准、拒绝或取消，以确保执行顺序可预测。

## 架构与职责

新增 `iris_agent/task_queue/`，仅负责排队、后台工作线程、取消协调与队列账本。现有 `iris_agent/task_center/` 继续负责任务时间线、状态转换和只读展示；它不保存完整用户消息。

```text
React 聊天
  └─ POST /api/tasks ──> TaskQueueService ──> data/task_queue/queue.json
                                   │
                                   ├─> TaskCenterService（状态与安全时间线）
                                   └─> 单工作者 ──> AgentService ──> 会话仓储
```

`TaskQueueService` 持有一个后台线程和条件变量。它每次只取队首作业，调用 `AgentService.run` 或 `AgentService.resolve_tool_approval`，将产生的事件映射到任务中心。任务中心仍是前端读取状态、队列位置和时间线的唯一来源。

## 数据与持久化

队列账本位于 `data/task_queue/queue.json`，使用临时文件替换实现原子写入。为在 Windows 上串行化跨进程读改写，目录允许额外存在内部 `queue.lock` 文件；它只承载一字节文件锁，不保存任务、用户消息或任何业务数据，也不通过 API 暴露。

队列条目包含：`task_id`、`session_id`、完整用户消息、提交时间和账本状态（`queued` 或 `active`）。完整用户消息仅用于服务重启后恢复尚未开始的排队作业；不通过任何任务 API 返回，也不写入任务中心事件。用户消息本来就由会话仓储持久化，队列账本不额外记录工具参数、工具返回值、环境变量、模型回复或原始异常。

任务中心新增 `queued` 状态，完整状态集合为：

- `queued`：已持久化，等待单工作者领取。
- `running`：工作者正在执行 Agent。
- `awaiting_approval`：等待工具审批，工作者不领取后续作业。
- `completed`、`failed`、`stopped`：终态。

列表按最后活动时间排序。队列位置只对 `queued` 项计算，按账本顺序从 1 开始；其他状态不返回队列位置。仍保留最多 100 条任务和每条最多 100 个安全事件的上限。

## 生命周期、审批与取消

1. `POST /api/tasks` 校验会话后，先创建状态为 `queued` 的任务中心记录，再原子写入队列账本并唤醒工作者。
2. 工作者领取作业时，先将账本条目置为 `active`，再将任务转为 `running` 并执行 Agent。条目仅在任务进入终态后删除；普通完成、错误和工具阶段沿用任务中心已有事件映射。
3. 遇到需审批工具时，任务变为 `awaiting_approval`。工作者停止领取后续作业，直到审批接口处理该调用。
4. 审批接口批准或拒绝后，任务回到 `running`，由同一工作者调用 `resolve_tool_approval` 继续执行。若再次请求审批，重复本流程。
5. `DELETE /api/tasks/{task_id}`：排队任务从账本移除并立即标记 `stopped`；等待审批任务会清除 Agent 的待审批调用并标记 `stopped`；运行中任务写入“已请求停止”安全事件，在当前模型请求或工具调用返回后的下一个可观察事件处停止并标记 `stopped`。一期不承诺中断正在阻塞的模型请求或工具进程。

服务启动时：

- 已在账本中且仍为 `queued` 的作业继续按原顺序等待执行。
- `active` 条目对应的 `running` 与 `awaiting_approval` 任务标记为 `stopped`，写入“服务重启，执行未完成”后删除该条目。
- 对应的内存审批状态不恢复；用户需重新提交该任务。

## HTTP API

新增接口：

| 接口 | 作用 |
| --- | --- |
| `POST /api/tasks` | 提交聊天任务，返回任务摘要和 `202 Accepted`。 |
| `GET /api/tasks?limit=50&session_id=<optional>` | 返回任务摘要、状态和排队位置。 |
| `GET /api/tasks/{task_id}` | 返回单项安全时间线和状态。 |
| `DELETE /api/tasks/{task_id}` | 请求停止或取消任务，返回最新任务摘要。 |
| `POST /api/tasks/{task_id}/tool-approvals/{call_id}` | 批准或拒绝当前任务的工具调用，返回最新任务摘要。 |

所有详情与列表响应仅使用任务中心的公共数据形状：请求摘要、状态、时间和固定安全事件。队列账本中的完整用户消息绝不出现在响应中。不存在的任务返回现有稳定格式的 404 错误；已完成、已失败或已停止的任务不能再次取消或审批。

## 前端体验

`useChat` 发送消息后不再保持 NDJSON 连接。它先将用户消息显示在聊天区，调用 `POST /api/tasks`，并保存当前任务 ID。

- `queued` 显示“排队中”；页面以短轮询查询该任务。
- `running` 显示“正在执行”；不展示逐字回复。
- `awaiting_approval` 显示现有工具审批卡片，并通过新的任务审批接口提交选择。
- 到达终态后停止轮询；`completed` 时重新读取会话，以完整回复替换等待状态；`failed` 或 `stopped` 显示安全提示与“查看任务”入口。

任务中心复用现有页面，增加 `queued` 标签、队列位置和取消入口。聊天中的“查看任务”继续跳转并选中当前任务。

## 错误处理与约束

- 队列账本写入失败时，提交接口不接受任务，并尽力将刚创建的任务中心记录标记为失败；不会启动未持久化的作业。
- 工作线程捕获未处理异常，将对应任务标记为 `failed`，记录固定失败摘要，并继续处理下一个任务。
- 同一任务的审批、取消与完成通过任务服务锁串行化；重复审批或对终态任务的操作返回冲突错误，不会再次执行工具。
- 任务取消只影响目标任务；不会删除会话、任务历史或其他排队作业。

## 测试与验收

后端测试覆盖：

- FIFO 执行、始终最多一个 Agent 运行，以及审批期间后续任务不启动；
- 创建后的立即查询、队列位置与完整生命周期；
- 批准、拒绝、重复审批和取消排队/等待审批/运行中任务；
- 重启后恢复排队任务，停止原运行或待审批任务；
- 账本原子写入、保留上限，以及工具参数、工具结果、环境变量、模型回复和原始异常不落盘；
- 新 API 的校验、404、冲突和任务中心数据脱敏。

前端测试覆盖：

- 提交后显示排队或执行状态，不再读取文本增量；
- 任务完成后刷新会话并展示完整回复；
- 审批、取消、失败与停止提示；
- 轮询在终态、切换会话和组件卸载时停止；
- 任务中心展示队列位置并可从聊天跳转。

验收标准是：连续提交的两个聊天任务按提交顺序完成；第一个任务需要审批时，第二个任务不会抢先开始；重启后未开始任务仍可执行；用户始终能查看安全时间线和最终完整回复，且敏感工具执行数据不出现在任何任务接口或账本中。
